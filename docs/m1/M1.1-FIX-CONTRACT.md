## 0. Credential terminology (use these exact terms in code comments, docs and runbooks)

| Term | Meaning | Where it may appear |
|---|---|---|
| **Runtime/app credential** | The restricted database role used by the HOME application (`home_app`). It owns no database objects. | The **only** database credential supplied to Vercel (`DATABASE_URL`, pooled connection). Local `.env.local` for running the app. |
| **Migration/admin credential** | The privileged database role used **only** for migrations and database administration (the Neon project owner role). | GitHub `production` environment secret `DATABASE_URL_MIGRATE` (direct connection), and a trusted machine for administration. **Never** supplied to the HOME application or the Vercel runtime. |

**Approved requirement (verbatim):** The runtime/app role must not own database objects and must not be able to disable the audit trigger, ALTER the audit table, UPDATE/DELETE/TRUNCATE audit rows, or otherwise defeat the append-only guarantee. The migration/admin role retains the privileges required for migrations. Integration tests must prove the restriction using the same role model used by the application.

## 1. Required before infrastructure

### 1.1 B1 — Gate sign-in requests before Better Auth, and close the HTTP surface

**Outcome:** a request for a non-household address, or any request over the rate limit, never reaches Better Auth, never creates a `verification` row, never stores the address, and cannot flood `audit_log`. Both entry points are covered.

**Design (required):**

1. **One gate, used by every entry point:** `src/trust/sign-in-gate.ts` exports `gateLinkRequest({ email, ip }): Promise<'send' | 'drop'>`, in this order:
   1. **Per-IP limit on every request**, household or not: 5 per 15 minutes (atomic, §2.3). Over the limit → `drop`.
   2. **Allowlist**: not a household address → `drop`.
   3. **Per-email limit** for household addresses: 5 per 15 minutes (atomic). Over the limit → `drop`.
   4. Otherwise → `send`.
2. **Server action** (`src/app/sign-in/actions.ts`): validate input, resolve the client IP (§2.2), call the gate, and call `auth.api.signInMagicLink` **only on `send`**. The person always sees the same confirmation.
3. **HTTP surface closed by allowlist of paths.** The route handler `src/app/api/auth/[...all]/route.ts` forwards to Better Auth **only** the paths HOME uses. Every other path returns 404 before Better Auth runs. In M1.1 that is exactly:
   - `GET /api/auth/magic-link/verify` (the emailed link).
   This removes `POST /sign-in/magic-link` from the public surface, so the server action is the only way to request a link. It also covers §2.1. Express the list as a constant with a comment; any future addition is a reviewed change.
   **Approved decision:** HOME exposes only the Better Auth HTTP endpoint required to verify an emailed magic link. Other Better Auth HTTP endpoints are not part of HOME's public auth surface.
4. **`sendMagicLink` keeps an allowlist check as defence in depth** (it should never see an outside address now). It no longer does rate limiting or denied-attempt auditing; those live in the gate.
5. **Denied-attempt auditing is capped:** at most **one** `auth.sign_in_denied` audit row per client IP per 15-minute window, with `meta: { stage, emailHash?, count: 1 }`. Further denials in the window are only logged (no email, IP hashed). Rate-limited requests are logged, not audited.

**Tests (required):**
- Integration: 20 requests for outside addresses from one IP through the gate and server-action code path → **0** new `verification` rows, **≤ 1** new `auth.sign_in_denied` row, no plaintext address anywhere in the database.
- Integration: 7 requests for a household address from one IP → exactly 5 links; from 7 different IPs → exactly 5 links (per-email limit).
- Integration: per-IP limit applies to household addresses too (6th request from one IP is dropped).
- Integration: a household address on a fresh IP still gets its link after another IP is limited.
- Integration/e2e: `POST /api/auth/sign-in/magic-link` → 404 and creates no rows; `GET /api/auth/get-session`, `POST /api/auth/update-user`, `POST /api/auth/sign-out`, `GET /api/auth/list-sessions` → 404.
- E2E: the existing sign-in, reuse, expiry and outsider scenarios still pass.

### 1.2 B2 — Vercel build correctness

**Outcome:** what Vercel uploads builds, and CI proves it on every PR.

- `tsconfig.json` is the **production** config used by `next build`: it excludes `tests/`, `playwright.config.ts`, `vitest.config.mts`, `scripts/`, `prototype/`.
- `tsconfig.test.json` extends it and includes everything; `pnpm typecheck` uses it (`tsc -p tsconfig.test.json --noEmit`), so tests stay type-checked.
- `scripts/vercel-bundle-check.mjs`: copies `git ls-files` minus the patterns in `.vercelignore` into a temporary directory (read the patterns from the file; support only the plain path/prefix patterns HOME uses, and **fail** on any unsupported pattern), runs `pnpm install --frozen-lockfile` and `pnpm build` there.
- CI job **`Vercel bundle build`** runs the script on every PR and on `main`.

**Tests:** the CI job itself. Verify locally that it fails on the current `main` (reproduces B2) and passes after the fix.

### 1.3 I1 — Repository privacy cleanup

### 1.4 I2 — Preview database isolation

**Rule (recorded in the runbooks and ADR 0003):** the dev/preview database is **never** derived from, reset from, or branched from production once real household data exists. It is rebuilt from **migrations + fixtures only**.

- **Approved decision:** preview/dev uses a **completely separate Neon project** (`home-dev`) from production, not a branch of the production project. Separate projects mean separate credentials, so accidental copying is impossible.
- **Runbook change:** describe the two projects (`home` for production, `home-dev` for previews and cloud-side development), each with its own runtime/app and migration/admin credentials (§0, §1.7). Remove "reset the branch from `main`" from `MIGRATIONS.md`. Document "rebuild dev" as: drop schema → `drizzle-kit migrate` → fixtures (none needed in M1).
- **Startup guard** in `src/lib/env.ts`:
  - New optional variables: `VERCEL_ENV` (set by Vercel: `production` | `preview` | `development`) and `HOME_PRODUCTION_DB_HOST`.
  - When `VERCEL_ENV === 'preview'`: `HOME_PRODUCTION_DB_HOST` is **required**, and the host of `DATABASE_URL` must **not** equal it. Otherwise refuse to start.
  - When `VERCEL_ENV === 'production'`: if `HOME_PRODUCTION_DB_HOST` is set, `DATABASE_URL`'s host must equal it.
- **Tests:** unit tests for preview refusing the production host, preview requiring the variable, production accepting its host, production refusing a mismatched host.

### 1.5 I3 — Production migration workflow hardening

- `.github/workflows/migrate.yml`:
  - Job condition `if: github.ref == 'refs/heads/main'`, so `workflow_dispatch` from any other branch does nothing.
  - Keep `environment: production`.
  - Pin **every** action to a full commit SHA with the version tag in a trailing comment. Resolve SHAs from the action repositories' tags (e.g. `git ls-remote https://github.com/actions/checkout refs/tags/v4.x.y`). Never guess a SHA.
- `.github/workflows/ci.yml`: pin every action to a full commit SHA in the same way, including the third-party `gitleaks/gitleaks-action` and `pnpm/action-setup`.
- Add `.github/dependabot.yml` for the `github-actions` ecosystem only (weekly), so pinned SHAs don't rot.
- `docs/runbooks/DEPLOY.md` §A.4 (owner action): `production` environment → **Deployment branches and tags: Selected branches → `main` only**, plus the required reviewer.
- **Test:** a grep-style CI check (or a unit test over the workflow files) that fails if any `uses:` line is not pinned to a 40-character SHA.

### 1.6 I4 — Destructive test database protection

- `tests/db-guard.ts` exports `assertTestDatabase(url)`. It accepts only URLs whose host is `localhost`, `127.0.0.1`, `::1` or `postgres` (CI service name) **and** whose database name ends in `_test`. Anything else throws, naming the reason but **not** echoing credentials.
- Call it before **any** destructive or test operation:
  - `tests/integration/global-setup.ts`
  - `tests/e2e/global-setup.ts`
  - `scripts/db-reset-test.mjs` (replace its regex)
  - `tests/integration/db.ts` (`testDb()`)
  - `playwright.config.ts` (before starting servers)
- `tests/setup.ts` **overrides** (not `??=`) `DATABASE_URL` with `TEST_DATABASE_URL` after asserting it. The other test variables also override, so nothing inherits from the developer's shell.
- **Negative tests** (unit) reject:
  - a Neon-style host with `neondb`
  - a remote host with `home_test`
  - `localhost` with database `home`
  - a malformed URL

  The error message must not contain the password.
- **Negative test** (unit or script-level): global setup with a non-test URL throws **before** any query runs (inject a fake client and assert it was never called).

### 1.7 I5 — Separate runtime/app role (required, approved)

**Outcome:** the HOME application connects with the runtime/app credential, which cannot defeat the append-only audit log even if it leaks. Migrations and administration use the migration/admin credential, which never reaches the application.

**Role model**

| Role | Credential | Privileges |
|---|---|---|
| Neon project owner role | Migration/admin credential | Owns schema `public` and every table; runs DDL and migrations. |
| `home_app` (`LOGIN`, `NOINHERIT`, no `CREATEDB`, no `CREATEROLE`, not a member of the owner role) | Runtime/app credential | `USAGE` on schema `public`; **no `CREATE`**. `SELECT, INSERT, UPDATE, DELETE` on `user`, `session`, `account`, `verification`, `rate_limit`. **`SELECT, INSERT` only** on `audit_log`. Owns **no** database objects. |

**Migration `0002_app_role.sql`** (run as the migration/admin role)
- Idempotent, and a no-op when `home_app` doesn't exist, so local, CI and both Neon projects all work:
  - `DO $$ BEGIN IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'home_app') THEN … END IF; END $$;`
- Inside it:
  - `REVOKE CREATE ON SCHEMA public FROM PUBLIC;`
  - `GRANT USAGE ON SCHEMA public TO home_app;`
  - The table grants above.
  - `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO home_app;` (run as the role that creates tables) so M2 tables are covered automatically.
  - **Explicitly** `REVOKE UPDATE, DELETE, TRUNCATE ON audit_log FROM home_app;` after the default grants.
- The trigger stays as the second layer.
- Rule for every future migration (record in `MIGRATIONS.md`): a migration that creates an append-only table must revoke `UPDATE, DELETE, TRUNCATE` on it from `home_app`.

**Local and CI use the same role model as production**
- `scripts/init-test-db.sql` (Docker) and the CI Postgres service create `home_app` with a known, test-only password and apply the same grants via the migrations.
- Two test URLs:
  - `TEST_DATABASE_URL`: migration/admin role, used **only** by global setup (reset + migrate) and fixture setup.
  - `TEST_APP_DATABASE_URL`: runtime/app role, used by **all** application code under test (`DATABASE_URL` in `tests/setup.ts`), integration tests of `src/trust/*` and the e2e dev servers.
- Both URLs pass the §1.6 test-database guard.

**Tests (integration, connected as `home_app`)**
- `INSERT` into `audit_log` succeeds; `SELECT` succeeds.
- `UPDATE`, `DELETE`, `TRUNCATE` on `audit_log` fail with **permission denied** (the role check, not the trigger).
- `ALTER TABLE audit_log DISABLE TRIGGER ALL` fails (must be owner); `DROP TRIGGER audit_log_no_update_delete ON audit_log` fails; `ALTER TABLE audit_log ADD COLUMN x int` fails.
- `CREATE TABLE` in `public` fails.
- `home_app` owns no objects: query `pg_class`/`pg_namespace` ownership and assert none.
- The full existing integration and e2e suites pass with application code running as `home_app`.

**Deployment implications (runbook, owner actions)**
- In **each** Neon project (production and `home-dev`), connected with the migration/admin credential, create `home_app`: `CREATE ROLE home_app LOGIN PASSWORD '<generated>' NOINHERIT;`. Generate the password; never commit it.
- First-time order per project: create `home_app` → run migrations with the migration/admin credential (grants apply) → configure Vercel with the runtime/app credential → deploy.
- Vercel `DATABASE_URL` = runtime/app credential, **pooled** connection string, for both Production and Preview (each pointing at its own project).
- GitHub `production` environment `DATABASE_URL_MIGRATE` = migration/admin credential, **direct** connection string.
- The migration/admin credential is never placed in Vercel. Add a startup check: if the connected role (`select current_user`) owns `audit_log`, the app refuses to start in production and preview (`VERCEL_ENV` set). Unit/integration test for the check.

## 2. Low-cost hardening (also required in M1.1)

### 2.1 Removed users and Better Auth endpoints
Closed by §1.1.3: no session-bearing Better Auth endpoint is reachable over HTTP. Add a comment in the route handler: any future endpoint added to the path allowlist must apply the allowlist check (`actorFor`) before forwarding. The e2e "removed user" test stays.

### 2.2 Trusted client IP
- `src/trust/client-ip.ts` exports `clientIp(headers): string | null`. Read **only** the header the deployment platform sets and documents as the client IP. On Vercel that is `x-real-ip`; confirm against Vercel's current documentation and record the source in a comment and ADR 0003.
- Accept exactly one syntactically valid IPv4/IPv6 address. Normalise IPv6 to a /64 bucket. Anything missing, multiple or invalid → `null`, and the gate uses a single shared bucket `ip:unknown` (fail closed).
- Configure Better Auth's `advanced.ipAddress.ipAddressHeaders` with the same header, so both agree.
- **Unit tests:** valid v4; valid v6 bucketed; spoofed multi-value header rejected; garbage rejected; missing → null.

### 2.3 Atomic rate limiting
- Replace check-then-increment with one statement: `INSERT … ON CONFLICT (key) DO UPDATE SET count = CASE WHEN last_request > window_start THEN count + 1 ELSE 1 END, last_request = now RETURNING count`. Allowed iff the returned `count <= max`.
- **Integration test:** 20 concurrent calls with `max = 5` → exactly 5 allowed.

### 2.4 Library logging cannot bypass redaction
- The Better Auth logger adapter in `src/trust/auth.ts` must **not** forward free-text messages. Map to a fixed event (`auth.library_warn` / `auth.library_error`) with a sanitised message: strip emails, URLs (including query strings) and long token-like strings, then truncate to 200 characters.
- Put the sanitiser in `src/lib/log.ts` (`sanitiseMessage`).
- **Unit test:** `"Invalid callbackURL: https://x.test/a?token=abc123 for sam@example.test"` → output contains none of the URL, the token or the email.
- Note in ADR 0003 that Better Auth may also call `console.*` directly in rare paths (e.g. plugin warnings at construction). These are configuration warnings without user data; accept them.

### 2.5 Production cookie attributes test
- Export a test-only factory from `src/trust/auth.ts` (e.g. `buildAuthForTest(envOverrides, deps)`) or make `buildAuth` accept an env object. Production code keeps using `getAuth()`.
- **Integration test:**
  - With a production-shaped env (`NODE_ENV=production`, `https://` URL, `provider` mail transport with mail sending stubbed), perform an in-process sign-in: request → capture link → `auth.handler(new Request(link))`.
  - Assert the session `Set-Cookie`:
    - name `__Secure-home.session_token`
    - `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`
    - `Max-Age=2592000`
    - no `Domain` attribute

### 2.6 Validate environment at server start
- Add `src/instrumentation.ts` with `register()` that, when `process.env.NEXT_RUNTIME === 'nodejs'`, parses the environment (`parseEnv(process.env)`) and throws on failure. Keep lazy access elsewhere.
- **Tests:**
  - Unit test: `register()` with an invalid env throws `EnvError`.
  - Script-level check (CI, in the bundle job or a small step): `next start` with a missing required variable exits non-zero or fails its first health request.
- Update DEPLOY.md: a misconfigured deployment fails at boot, visible in Vercel's runtime logs.

### 2.7 Postmark tracking off
`docs/runbooks/DEPLOY.md` §A.2: in the Postmark server's settings, **disable open tracking and link tracking** for the outbound stream used for sign-in. Sign-in links must never pass through a tracking redirect. Add this to the smoke checklist: "the received link points directly at the HOME domain".

### 2.8 Activity time zone
`src/app/(home)/settings/activity/page.tsx` uses `env.HOME_TIMEZONE`. No hard-coded zone anywhere in `src/`. Lint or grep test: `Pacific/Auckland` appears in `src/` only in `lib/env.ts`'s default.

### 2.9 Deterministic audit pagination
- `listAudit` takes a cursor `{ at: Date, id: string }` and filters with `(at, id) < (cursor.at, cursor.id)`, ordered by `at desc, id desc`. Return the next cursor with the page.
- **Integration test:** insert rows with **identical** `at` (explicit timestamp) across a page boundary → paging returns every row exactly once.

## 3. Architectural decisions recorded by M1.1

**A. Fixed 30-day sessions (amends M1-D3).**
- Sessions last 30 days from sign-in and are **not** extended by use. Set `session.expiresIn = 30 days` and `session.disableSessionRefresh = true`. This is an intentional simplification for V0.1.
- Update ADR 0003, `docs/m1/M1-BUILD-CONTRACT.md` §3 (M1-D3) and §5.1, and `docs/runbooks/DEPLOY.md`.
- **Test:** after `getSession` calls with the session's `updated_at` moved back by more than a day, `expires_at` is unchanged. The cookie `Max-Age` stays 30 days (covered by §2.5).

**B. Separate runtime/app role (I5) — approved, required in M1.1 before infrastructure setup.** Specified in §1.7, using the credential terminology in §0.

**C. Git history is not rewritten** to remove the already-committed name or commit-author email. Current tracked content must contain no real household information, and the owner enables GitHub email privacy (§1.3).

**D. Public auth surface — approved.** Only the Better Auth HTTP endpoint that verifies an emailed magic link is exposed (§1.1.3).

**E. Preview/dev database — approved.** A completely separate Neon project, not a branch of production (§1.4).
