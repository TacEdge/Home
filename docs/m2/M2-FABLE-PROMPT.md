## Rules

- **Implement only the contract.** No UI, no Kev, no integrations, no calendar tables, no recurrence handling, no purge execution, no backups or export, no M3 work.
- **One PR at a time, in the contract's work-package order (§2.2):** Package S, then 2a → 2b → 3a → 3b → 4a → 4b → 5a → 5b.
- **Migration-first (§2.1).** A migration PR contains no application code that requires its schema. Never open, or ask to merge, an application PR whose schema has not yet been migrated in production: check that the **Migrate production database** run for it succeeded, and link it in the PR description.
- **Never merge.** Each PR stops when CI is green and is ready for review. The owner merges it (D-M2-7). Start the next PR only after the owner confirms the previous one is merged, and branch it from the updated `main`. Always confirm the base branch is `main` and current immediately before opening a PR.
- **PR #17 is not a source.** It was merged only into an obsolete branch (contract §2.3). Rebuild from `main`; do not copy its code without re-reviewing it against the carry-forward findings in §2.3.
- **Never change M1 security controls**, credentials, workflows, or Vercel, Neon, Postmark or GitHub settings. Never touch Better Auth-owned tables.
- **Migrations are additive only**, one per migration PR, generated by drizzle-kit, with hand-written SQL after a statement breakpoint. Production is live: every migration must be safe against the app already deployed, and every application PR must be safe against `main`'s schema (the previous-schema CI check).
- **No new runtime dependency.** If one seems necessary, stop and ask.
- **No real household information** anywhere: code, docs, tests, fixtures, commits, PR text. The fixture family and `@example.test` addresses only.
- **The contract rules in §3.2 (P-1…P-6) are approved**, P-1 as refined by the owner. Implement them exactly as written there.

## How to work

Within each PR, take one contract item at a time:

1. Re-read the item and its tests (contract §8).
2. Write the test first where possible, especially the leak, refusal and append-only tests, and confirm it fails before the code exists.
3. Implement.
4. Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration` and `pnpm test:e2e`. All existing tests stay green. Never skip, weaken or delete a test to get green.
5. Re-read your diff adversarially against the contract, `CLAUDE.md` rules 1, 3, 8, 9 and 11, and §5 of the contract.
6. Commit with a focused message.

Open the PR against `main`. The description lists the contract items covered, the tests that prove them, the migration and what it adds, and any deviation with its reason. Then wait for CI. Fix and push until it is green. Then stop and report.

## Points to get right

- **Query-level privacy.** Visibility, archive state and sensitivity are SQL predicates. A record the actor cannot see is a `NotFoundError`, identical to a missing one.
- **Audit follows the record (P-1).** Audit metadata never reveals more than the affected record would. `listAudit` shows a domain row only to someone who can currently see that record, whoever acted; the write-time snapshot decides only once the record is gone. Summaries and meta are structural: no title, name, text, captured words, payload or proposal summary.
- **Kev cannot write.** Every write refuses `via: 'kev'` except `captureVerbatim` and `proposals.create`. Only a `via: 'ui'` requester can approve.
- **Approval is atomic.** Payload re-validated, write executed through the target service, status and audit in one transaction. No partial writes.
- **Captures are verbatim and private.** Store the text exactly as given.
- **Household never references private.**
- **Retention readiness.** Every timestamp and foreign-key behaviour in contract §4.4 exists, even though nothing purges yet.
- **The seed refuses non-local databases** and never prints a connection string.
