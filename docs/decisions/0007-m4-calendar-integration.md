# ADR 0007 — M4 calendar integration: scope, security boundaries and decisions

Status: **Accepted**, 2026-10-05 (owner approved the M4 readiness plan with decisions 1–6 as recorded here). Contract: `docs/m4/M4-BUILD-CONTRACT.md`.

## Context

M3's code is complete (Packages 0–10, PRs #30–#40); its owner acceptance is open, waiting on the restore rehearsal (DEPLOY.md §E items 7–8). M1 is deployed but not accepted (§E items 1–6). The Production real-data gate is closed (ADR 0006 §2).

The repository already settles M4's strategy: Google Calendar first through its secret iCal address with a provider-neutral `CalendarProvider` (ADR 0001 D1); read-only sync, lazy refresh on read at about 15 minutes, no background jobs (SYSTEM-ARCHITECTURE §2.4); application-level encryption of integration credentials (§5.7); external text as untrusted data (§5.5); CalendarConnection and CalendarSource deferred to M4 with credential encryption (ADR 0005 §3); imported recurrence, feed exceptions, manual single-occurrence edits and regular-week derivation in M4 (ADR 0005 §4, ADR 0006 §3); and a nonce-based script CSP before the first untrusted external content (ADR 0003 §9).

Two things in the existing documents needed correcting before M4 can be built: FAMILY-DATA-MODEL said synced records have no `created_by`, which would make a private calendar invisible even to its owner under the visibility predicate; and SYSTEM-ARCHITECTURE listed iCloud and Outlook secret addresses alongside Google's for V0.1.

## Decisions

1. **M4 development proceeds on synthetic data; real calendars stay gated.** As ADR 0006 §1: M4 is built and tested in local and Preview while M1 and M3 owner acceptance remain open. Connecting a calendar and every sync write are family-domain writes, refused in Production while `HOME_REAL_DATA` is closed. No real family calendar is connected in any environment until the gate permits it, and never in Preview.
2. **Preview test calendar (owner decision 1, approved).** A dedicated throwaway Google account owned by the owner holds a calendar of synthetic events only. Its secret address is a Preview-only credential: entered through Preview's Settings › Calendars, encrypted with Preview's key, never committed or written into an issue, PR, log or screenshot. No real family or personal data.
3. **Allowed outbound hosts (owner decision 2, modified).** M4 accepts, in Production and Preview, only the Google Calendar host and address shape required for the secret iCal feed (`https://calendar.google.com/calendar/ical/…/private-…/basic.ics`, with `webcal://` rewritten). iCloud, Outlook and any other real feed are **not** enabled in M4 merely because they serve ICS; each future real provider needs an explicit later decision. The adapter stays provider-neutral, and tests use synthetic feeds of any shape through an injected fetcher or the fake provider. No environment variable widens the allowlist in any deployed environment.
4. **Audit granularity (owner decision 4, approved).** One structural audit row per calendar refresh (`calendar.sync`), with counts only: added, changed, archived, restored, skipped, and the status. Activity is never flooded with a row per imported event. No provider text or credential ever enters audit metadata or summaries. Connection and source changes are audited one row each, structurally. CLAUDE.md rule 8 (every write audited) is met: each refresh's writes are recorded by its row.
5. **Disconnect (owner decision 3, modified).** Disconnecting does **not** hard-delete mirrored events. In one transaction: the stored credential is destroyed (ciphertext cleared), the connection is marked disconnected, its source is archived, and its mirrored events are archived. HOME-owned annotations (`event_person`) and notes are preserved. When the **same source is reliably reconnected** (the same address, recognised by its keyed fingerprint, by the same owner), the source returns and the next refresh restores and updates matching mirrored events by identity, so annotations and notes survive. Permanent purge waits for the later retention mechanism (ADR 0006 §8).
6. **Duplicate calendars (owner decision 5, modified).** HOME does not deduplicate events across distinct calendar sources because their UID or recurrence id matches: external UIDs are not assumed globally unique across unrelated sources. An exact duplicate secret address is refused when HOME can prove it (its keyed fingerprint matches a live connection); otherwise each source keeps its identity and duplicates are allowed rather than risk an incorrect merge. Cross-source fingerprinting or deduplication of events is deferred until a reliable identity mechanism exists.
7. **Attendees and organisers (owner decision 6, approved).** External attendee and organiser identities are never imported. Who is going and who is responsible stay HOME-owned (`event_person`).
8. **Sync ownership rule (correction).** A synced event has `created_by` = the calendar connection's owner, `created_via` = `sync`, and the visibility of its calendar source. The normal HOME visibility predicate then applies unchanged: a private calendar's events are its owner's alone; a household calendar's are both adults'. There is no parallel privacy system for calendar events. Sync writes run as the owner's user actor with `via: 'sync'`, minted only by the sync service, and pass through `auditedWrite` like every other write (gate, audit, Kev refusal). This corrects FAMILY-DATA-MODEL §2, which said `created_by` is null for sync.
9. **Untrusted content rule.** Imported title, description, location and any other provider text are untrusted external data. The adapter strips HTML and stores bounded plain text (the existing event limits). React's escaping and the nonce-based script CSP together form the rendering boundary. External calendar content is never treated as instructions by any part of HOME, and when Kev arrives (M8) calendar and provider text must reach it marked as untrusted context.
10. **Nonce-based script CSP first.** ADR 0003 §9's prerequisite is M4 Package 1, before any code that fetches or renders external content.
11. **Credentials.** The secret address is sealed with AES-256-GCM (Node `crypto`), a random IV, a key id, and the connection and owner ids as associated data; the key is `HOME_CREDENTIALS_KEY`, different per environment and never committed, with an optional previous key for rotation. A keyed HMAC fingerprint of the normalised address recognises the same address without storing it in plain text. The address, ciphertext and fingerprint never reach the client, logs, audit, Activity, exports, error copy or LLM context. A missing key refuses calendar writes calmly and never fails boot.
12. **Refresh on use.** Rendering never writes. When a source the signed-in adult can see is older than 15 minutes, the page asks a same-origin, uncached route to refresh it without waiting; Refresh now works without JavaScript. Any adult's use may refresh a household source; a private source refreshes only on its owner's use; the writes are always the owner's. One refresh per source at a time; each refresh is one transaction, so a failure changes nothing and last-known events stay.
13. **Identity, removal and overrides.** A synced event's identity is its source, its external UID and its original occurrence (empty for a series or single event), enforced by a unique index. The same identity is the same row across refreshes. Missing from a successful feed: archived. Back: restored. New UID: new row. A moved or changed occurrence is its own row pointing at its series, with its original occurrence added to the series' exdates; a cancelled occurrence is an exdate. The same override model serves manual single-occurrence edits.
14. **Default people are derived.** A source's default people are shown for its events that have no annotations of their own; they are never written as annotations.
15. **Scope.** M4 keeps manual single-occurrence edits and regular-week derivation (already settled). It adds no calendar write, background job, authenticated provider API, cross-source deduplication, attendee import, purge, or M5–M8 feature (including the `data_health` insight: freshness is a factual line, not an insight). The one new runtime dependency is `node-ical` (approved stack).
16. **Packages and implementers.** 0 contract (Opus); 1 nonce CSP (Opus); 2 credentials and safe fetch (Opus); 3 provider layer and recurrence extension (Opus); 4a migration only (Opus); 4b services and sync (Opus); 5 Settings › Calendars (Fable); 6 synced events across screens (Fable); 7 regular week (Opus); 8a single-occurrence engine and service (Opus); 8b its screens (Fable); 9 acceptance and audit (Opus). Packages are acceptance boundaries and may be split into smaller PRs. Migration-first: 4a merges and runs in Production and Preview before 4b or 8a merges.

## Consequences

- FAMILY-DATA-MODEL: synced records carry the connection owner as `created_by`; CalendarConnection and CalendarSource move back into active scope with the fields above; the override model is noted; EventPerson on synced series uses stable event rows.
- SYSTEM-ARCHITECTURE §2.4: the ICS adapter accepts Google's secret address only in M4; other real feeds need a later decision; refresh on use without blocking render; no attendees in the normalised event.
- ROADMAP, CLAUDE.md and README: M3 code complete with owner acceptance and the gate open; M4 in progress on synthetic data.
- DEPLOY.md: §E notes that no calendar credential exists in Production until the gate opens and M4 is accepted; Package 2 adds `HOME_CREDENTIALS_KEY` to the env table; Package 9 adds M4's rows to §E.
- ADR 0003 §9's nonce CSP is delivered by M4 Package 1.
